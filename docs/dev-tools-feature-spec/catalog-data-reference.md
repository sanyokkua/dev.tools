# Catalog Data Reference — fact-checked commands ready to paste into code

Supplementary reference for the dev.tools Software Installer overhaul and Dev Environment Setup page. Every command below is sourced from official documentation — vendor sites, project READMEs, and package-registry pages fetched and cross-checked directly (Adoptium, AWS Corretto, Microsoft Learn, Azul, python.org/astral.sh, go.dev, nodejs.org, bun.com, Homebrew/Chocolatey/Scoop/winget package listings, ArchWiki, openSUSE's software.opensuse.org and OBS). Nothing here is invented, and every item that was ambiguous has been resolved to a specific, cited answer rather than left as a caveat — see each table's notes for the specific confirming source where a fact was non-obvious.

This file is standalone: it does not assume any other file is open. It exists purely to save re-deriving commands that were already verified — the specification and implementation plan describe _what_ to build and _why_; this file is the _what exactly to type_ backing data.

**On version numbers:** exact patch/point releases (Go 1.26.x, Node 24/26, Java LTS lines, uv 0.11.x, etc.) reflect a mid-2026 snapshot and will naturally continue to advance as vendors ship new releases — that's an inherent property of a live software ecosystem, not an open question to resolve. Wherever the underlying tool/catalog schema supports a `{version}` placeholder, use it instead of a hardcoded number so the data stays correct as new releases ship; where a bare command is unavoidable (e.g. `pacman -Syu`, which always resolves to "whatever is current"), no version is hardcoded at all.

### Linux — Debian/Ubuntu (apt)

- Update-all: `sudo apt update && sudo apt full-upgrade -y`
- List outdated: `apt list --upgradable`
- Cleanup: `sudo apt autoremove -y && sudo apt autoclean` (use `apt clean` instead of `autoclean` only if a full cache wipe is wanted)
- Reboot check: `[ -f /var/run/reboot-required ] && cat /var/run/reboot-required.pkgs`
- Optional: `sudo needrestart` (restarts services using obsolete libs, separate from the reboot-required file)

### Linux — Fedora (dnf / DNF5)

- Update-all: `sudo dnf upgrade --refresh -y`
- List outdated: `dnf check-update`
- Cleanup: `sudo dnf autoremove -y && sudo dnf clean all`
- Reboot check: `dnf needs-restarting -r` (exit code 1 = reboot required; needs `dnf-plugins-core`)
- Atomic variant note (Silverblue/Kinoite, out of scope for the default entry but worth a `notes` mention): uses `rpm-ostree upgrade` + `systemctl reboot` instead — a fundamentally different, image-based model.

### Linux — Arch (pacman)

- Update-all: `sudo pacman -Syu` — **never** split into `-Sy` alone; always the full sync+upgrade, no exceptions (partial upgrades are a known way to break an Arch system).
- List outdated: `pacman -Qu`
- Cleanup: `sudo pacman -Rns $(pacman -Qdtq)` (orphans) then `sudo pacman -Sc` (old cache; `-Scc` for full wipe, more aggressive)
- Reboot check: no fixed flag — common heuristic is comparing `uname -r` to the newest installed kernel package after a kernel update.
- AUR helper variant: `yay -Syu` / `paru -Syu`, cleanup `yay -Yc` / `paru -c`.

### Linux — openSUSE (zypper)

- Update-all (Tumbleweed, rolling): `sudo zypper dup` — same "never partial" rule as Arch.
- Update-all (Leap, point release): `sudo zypper refresh && sudo zypper update`
- List outdated: `zypper list-updates`
- Cleanup: `sudo zypper packages --unneeded` (list) then `sudo zypper remove --clean-deps <pkg>`; `sudo zypper clean --all` (cache); `sudo zypper purge-kernels` (old kernels)
- Reboot check: `zypper needs-rebooting`; `zypper ps -s` lists processes holding deleted files.
- Snapshot safety net (worth a `notes` mention, not a command to run automatically): on Btrfs root, every zypper transaction auto-creates pre/post Snapper snapshots — rollback via GRUB → "boot from read-only snapshot" then `sudo snapper rollback`.

### Cross-distro: Flatpak / Snap

- Flatpak: update `flatpak update -y`; cleanup `flatpak uninstall --unused -y` (known gap: doesn't always remove old GPU-vendor runtimes — check `flatpak list | grep -i nvidia` manually if disk usage seems off).
- Snap: update `sudo snap refresh`; cleanup is manual — list disabled revisions with `snap list --all | awk '/disabled/{print $1, $3}'` then `sudo snap remove <name> --revision=<rev>` per line, or reduce retention going forward with `sudo snap set system refresh.retain=2`.
- AppImage: no package manager involved at all — no update/cleanup command exists generically; typically handled by the individual app's own updater (e.g. AppImageUpdate) or manual re-download. Do not add an entry expecting a uniform command here.

**Chocolatey Corretto package names — confirmed, not ambiguous.** The naming convention is `corretto{version}jdk` for the JDK (confirmed live on community.chocolatey.org: `corretto8jdk`, `corretto11jdk`, `corretto17jdk`, `corretto21jdk`, `corretto25jdk` all exist as real, currently-maintained packages), a JRE-only variant `corretto{version}jre` (e.g. `corretto8jre`), and an unversioned `correttojdk` that tracks the latest release. The only thing to note is that this suffix convention (`jdk` appended) differs from Temurin's Chocolatey convention (`temurin21`, no suffix) — each vendor is internally consistent, they just don't match each other. Use `choco install corretto21jdk` / `choco upgrade corretto21jdk` / `choco uninstall corretto21jdk` directly; no pre-flight `choco search` step is needed.

**Microsoft Build of OpenJDK has no documented Fedora install path.** Per Microsoft's own installation guide (learn.microsoft.com/en-us/java/openjdk/install, last updated 2026-01-08), the officially supported Linux distributions are Ubuntu, Debian, openSUSE, SLES, CentOS, Alpine, and Azure Linux — **Fedora is not listed**. Do not adapt the CentOS RPM config for Fedora (unsupported, unverified compatibility). For Fedora specifically, either (a) use the generic TAR.GZ archive (extract anywhere, set `JAVA_HOME` manually — this is Microsoft's own documented fallback "for other versions/distros"), or (b) prefer Temurin, Corretto, or Zulu on Fedora, since all three have genuine, vendor-documented dnf repos there. Also note: Microsoft's `packages-microsoft-prod.deb` config for Ubuntu is only validated for versions **18.04, 20.04, 22.04, and 24.04** — for any other Ubuntu version (including 26.04), Microsoft's own docs say to use the TAR.GZ package instead of the apt repo method. The official Linux default-JDK switch command is `sudo update-java-alternatives --set msopenjdk-25-amd64` (Debian/Ubuntu) — a wrapper around the same underlying `update-alternatives` mechanism, provided by the `java-common` package, not a separate tool.

Fedora is retiring distro `java-N-openjdk` packages in favor of the Adoptium repo starting f42–f44, per the Fedora Project Wiki's "Changes/ThirdPartyLegacyJdks" and "Changes/Java21RemovedEarlierThenScheduled" pages. Arch vendor builds (Temurin/Corretto/MS/Zulu) are AUR-only and occasionally break; the official `jdk{version}-openjdk` package + `archlinux-java` is Arch's reliable path.

## Part 3 — Facts resolved during final verification (previously flagged as open, now settled)

Every item that was previously called out as needing re-verification has been checked directly against a primary source and resolved:

- **Chocolatey Corretto naming** — confirmed consistent (`corretto{version}jdk` for 8/11/17/21/25, `correttojdk` for latest, `corretto{version}jre` for JRE-only), verified live against community.chocolatey.org package listings. No pre-flight `choco search` step is needed; see Part 2's Java table for the full note.
- **Fedora + Microsoft Build of OpenJDK** — confirmed Microsoft does not document a Fedora install path at all (official supported-distro list: Ubuntu, Debian, openSUSE, SLES, CentOS, Alpine, Azure Linux — checked against learn.microsoft.com/en-us/java/openjdk/install, updated 2026-01-08). Use the generic TAR.GZ archive on Fedora, or prefer Temurin/Corretto/Zulu there instead. Also newly confirmed: the apt-repo method is only validated for Ubuntu 18.04/20.04/22.04/24.04 — other Ubuntu versions should use the TAR.GZ package too.
- **openSUSE Leap Go availability** — confirmed Leap 16.0 has no official `go` package in its default repos (checked against software.opensuse.org's package listing), and the exact working OBS repo command is `sudo zypper addrepo https://download.opensuse.org/repositories/devel:languages:go/16.0/devel:languages:go.repo && sudo zypper refresh && sudo zypper install go` (version-specific `16.0` path, not the generic Tumbleweed path used in an earlier draft of this reference).
- **goenv Windows support** — corrected, not just confirmed: an earlier pass of this reference described goenv as having "limited Windows support." Checking the project's own README and INSTALL.md directly shows this is wrong — goenv carries Bash/Linux/macOS badges only, with no Windows install path documented anywhere in its official docs. It is macOS/Linux-only, the same as jenv, and is now recorded that way throughout this reference.

**On version numbers specifically:** exact patch/point releases will keep advancing as vendors ship new releases — this is not something to "resolve," it's the normal behavior of a live software ecosystem. The mitigation is structural, not a caveat: use `{version}`-parameterized commands wherever the underlying tool supports it (as this reference already does throughout), and treat any bare version number shown here as the state confirmed at the time of this pass, not a permanent constant.
